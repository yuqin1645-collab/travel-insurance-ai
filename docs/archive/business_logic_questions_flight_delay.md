## ✅ 已确认的业务规则（代码已实现 2026-05-11）

### 规则1: 延误计算口径

**业务确认**: 延误时长 = max(改签航班实际起飞时间 - 原航班计划起飞时间, 改签航班实际到达时间 - 原航班计划到达时间)

**代码实现**: [delay_calc.py:307-328](app/modules/flight_delay/stages/delay_calc.py#L307-L328) 口径2已正确实现。

### 规则2: 单程改多程场景

**业务确认**: 原航班只有一程，改签后变成多程，不管机场是否匹配都要计算。用原航班的起飞地/到达地计划时间 vs 改签航班实际时间。

**代码实现**: [delay_calc.py:281-325](app/modules/flight_delay/stages/delay_calc.py#L281-L325) — 移除机场匹配阻断，改为记录不匹配信息但继续计算。

### 规则3: 多次改签取实际乘坐航班

**业务确认**: 中间改签多次，以被保险人实际乘坐的航班（从登机牌提取）为准进行计算。

**代码实现**: [vision_merge.py:206-230](app/modules/flight_delay/stages/vision_merge.py#L206-L230) — 登机牌数据作为实际乘坐航班的权威来源，覆盖chain填充的值。

### 规则4: 联程多程看末程

**业务确认**: 联程场景下，只看末程的起飞地和到达地，与乘客实际乘坐的航班进行计算。

**代码实现**: 
- [vision_merge.py:30-61](app/modules/flight_delay/stages/vision_merge.py#L30-L61) — 从itinerary_segments提取末程机场
- [delay_calc.py:287-290](app/modules/flight_delay/stages/delay_calc.py#L287-L290) — 使用末程机场做匹配

### 规则5: 中转接驳免责因果检查

**业务确认**: 不管延误时长够不够，都要检查是否前序航班延误导致到达中转站时间延后，压缩或耗尽原定转机时间，造成赶不上后续航班。

**代码实现**: [hardcheck.py:536-600](app/modules/flight_delay/stages/hardcheck.py#L536-L600) — 因果检查优先于改签豁免，只有确认前程正常到达时才不触发免责。

## 待确认：BL-001: 国际联程国内段的保障范围

### 案件示例

| 字段 | 内容 |
|------|------|
| ForceID | a0nC800000ODl1hIAD |
| 险种 | 航班延误 |
| AI审核结果 | 通过，延误9小时，赔付300元 |
| 人工审核结果 | **拒绝** |

### 人工拒绝理由

> "会员权益仅保障国际直飞航班延误，本次申请取消航班MU6531为国内段航班，且依据权益免除责任（权益人因乘坐前次航班的任何延误，导致其未能准时搭乘到原预定的接驳航班所造成的航班中转延误），本次申请未达赔付标准"

### 问题分析

1. 旅客购买了**国际联程机票**（如 上海→香港→昆明）
2. 其中**国内段**（MU6531：香港→昆明）取消/延误
3. AI认为这是国际行程的一部分，予以通过
4. 人工认为"会员权益仅保障国际直飞航班延误"，国内段不在保障范围内

### 需要业务确认的问题

1. **国际联程中的国内段航班**（如HKG→KMG）的延误/取消，是否在航班延误权益的保障范围内？
2. "国际直飞航班"的准确定义是什么？是否包含联程航班中的境内段？
3. 如果不包含，AI应通过什么条件识别这类案件并拒绝？

### 建议AI审核规则（待业务确认）

如果业务确认"国际联程中的国内段不在保障范围内"，建议规则为：

> 当旅客为国际联程行程（出发地或目的地有一方在境外），但理赔焦点航班为境内段（出发地和目的地都在中国境内或特别行政区）时，适用"仅保障国际段"规则，不予赔付。

## BL-002: 改签场景的延误定义 ⭐ 最大影响

### 案件示例

| 字段 | 案件A | 案件B | 案件C |
|------|-------|-------|-------|
| ForceID | a0nC800000IbiPVIAZ | a0nC800000IViDhIAL | a0nC800000JIVDjIAP |
| 原航班 | SK4095 (2/27) | AF1101 (2/22) | MS878 (1/5) |
| 原航班延误 | 1h58m | 1h8m | 3h22m |
| AI计算延误 | 12h32m | 16h54m | 14h |
| AI赔付金额 | 600元 | 900元 | 600元 |
| AI审核结果 | **通过** | **通过** | **通过** |
| 人工审核结果 | **拒绝** | **拒绝** | **拒绝** |

### 人工拒绝理由

- IbiPVIAZ: "SK4095起飞延误1小时58分钟，到达延误1小时34分钟，**未达到起赔标准5小时**"
- IViDhIAL: "AF1101起飞延误1小时8分钟，到达延误48分钟，**未达到起赔标准5小时**"
- JIVDjIAP: "MS878延误3小时22分钟，**未达到起赔标准5小时**"

### 问题分析

**同一个案件，两种延误计算口径：**

| 口径 | 计算方式 | IbiPVIAZ结果 | 是否≥5小时 |
|------|---------|-------------|-----------|
| 人工口径 | 原航班实际起飞 - 原航班计划起飞 | 1h58m | ❌ 未达 |
| AI口径 | 改签航班实际到达 - 原航班计划到达 | 12h32m | ✅ 达到 |

**核心分歧：航班延误权益中的"延误5小时"是指什么？**

- **理解A（人工口径）**：原航班自身的延误程度。原航班延误不足5小时，即使改签后总延误很大，也不赔。
- **理解B（AI口径）**：旅客最终经历的总延误。原航班取消/延误导致旅客最终晚到超过5小时，应该赔。

### 需要业务确认的问题

1. **条款中"航班延误5小时"的定义**：
   - 是指原航班自身的延误（计划起飞→实际起飞）？
   - 还是指旅客最终到达的总延误（原计划到达→改签后实际到达）？

2. **改签场景的赔付标准**：
   - 如果原航班延误 < 5小时，但改签后总延误 > 5小时，是否应该赔付？
   - 如果应该赔付，赔付档位按哪个延误时长计算？

3. **条款是否明确区分了"航班延误"和"旅行延误"**：
   - "航班延误" = 单个航班自身的延误
   - "旅行延误" = 旅客从出发地到目的地的总延误
   - 本权益保障的是哪一种？

### 两种理解对数据库的影响预估

| 理解 | 影响的P0案件 | 影响的P2案件 | 总体影响 |
|------|-------------|-------------|---------|
| 按原航班延误（人工口径） | 2件P0变为一致 | ~100件P2变为一致 | 一致率从58.5%提升至约70% |
| 按总延误（AI口径） | 维持现状 | 需人工审核标准调整 | 需要与业务部门对齐 |

### 建议AI审核规则（待业务确认）

**方案A：采用人工口径（原航班延误）**

> 当原航班存在改签场景时，起赔门槛（5小时）的判定以原航班自身延误为准：
> - 原航班延误 ≥ 5小时 → 进入赔付计算，按改签后总延误计算赔付档位
> - 原航班延误 < 5小时 → 不予赔付（即使改签后总延误 > 5小时）

**方案B：采用AI口径（总延误）**

> 当原航班存在改签场景时，起赔门槛和赔付计算均以旅客最终经历的总延误为准：
> - 改签后总延误 ≥ 5小时 → 按总延误计算赔付档位
> - 需额外检查中转接驳免责条款是否适用

## BL-003: 中转接驳免责的触发条件

### 案件示例

以下案件人工均引用了中转接驳免责条款：

| ForceID | 原航班 | 原航班延误 | 人工备注摘要 |
|---------|--------|-----------|-------------|
| a0nC800000IbiPVIAZ | SK4095 | 1h58m | "且依据权益免除责任（中转接驳延误）" |
| a0nC800000IViDhIAL | AF1101 | 1h8m | "且依据权益免除责任（中转接驳延误）" |
| a0nC800000JIVDjIAP | MS878 | 3h22m | "且依据权益免除责任（中转接驳延误）" |
| a0nC800000ODl1hIAD | MU6531 | 取消 | "且依据权益免除责任（中转接驳延误）" |

### 免责条款原文

> "权益人因乘坐前次航班的任何延误，导致其未能准时搭乘到原预定的接驳航班所造成的航班中转延误"

### 问题分析

1. 人工在拒绝时，**同时引用了两个理由**：
   - 理由1：原航班延误未达5小时（BL-002问题）
   - 理由2：中转接驳免责

2. 这意味着即使延误达到了5小时，人工可能仍然会以中转接驳免责为由拒绝

3. AI的中转接驳检测（`missed_connection_check`）依赖于：
   - Vision抽取的`mentions_missed_connection`标记
   - AI解析的`delay_reason`中的关键词
   - 旅客行程是否为联程

4. 部分案件中，这些条件未满足，导致中转接驳免责未被触发

### 需要业务确认的问题

1. **中转接驳免责的完整触发条件**：
   - 是否只要旅客有联程航班 + 发生了改签/误机，就触发此免责？
   - 还是需要前序航班延误达到一定时长才触发？
   - 如果前序航班延误很短（如15分钟），但旅客仍然错过了后续接驳航班，是否触发？

2. **"前次航班的任何延误"的理解**：
   - "任何延误"是否包含1分钟的延误？
   - 还是需要一个最低延误门槛（如30分钟以上）？

3. **免责的适用范围**：
   - 免责是否仅适用于"前序延误导致误机"的场景？
   - 如果前序航班正常到达，但末段航班独立取消，是否适用此免责？
   - 如果原航班取消（非延误），航司安排改签，是否适用此免责？

### 建议AI审核规则（待业务确认）

**中转接驳免责的判定流程（建议）：**

```
1. 旅客是否为联程行程？
   NO → 不触发
   YES → 继续

2. 是否发生了误机/改签/行程变更？
   NO → 不触发
   YES → 继续

3. 前序航班是否有延误/取消？
   NO（末段独立事件）→ 不触发
   YES → 继续

4. 前序航班延误/取消是否导致旅客无法搭乘末段航班？
   NO → 不触发
   YES → 触发中转接驳免责
```

## BL-004: 验证中发现的持续业务逻辑分歧（2026-05-12更新）

> 在第2轮10样本验证中，3个P0案件（JIVDjIAP, IViDhIAL, IbiPVIAZ）即使代码已按业务确认规则正确实现，仍然与人工不一致。根因是**人工审核标准未与业务规则同步**。

### 案件1: a0nC800000JIVDjIAP（P0）

| 字段 | 内容 |
|------|------|
| **ForceID** | a0nC800000JIVDjIAP |
| **险种** | 航班延误 |
| **AI审核结果** | 通过，延误14小时（840分钟），赔付600元 |
| **人工审核结果** | **拒绝** |
| **人工备注** | "根据提供的材料，1月5日航班MS878延误3小时22分钟，未达到起赔标准5小时，后续航班MS955正常执飞，且依据权益免除责任（权益人因乘坐前次航班的任何延误，导致其未能准时搭乘到原预定的接驳航班所造成的航班中转延误），本次申请未达赔付标准" |

**代码逻辑**：
1. 规则1（延误计算口径）：延误 = max(改签起飞延误, 改签到达延误) = max(840, 825) = 840分钟 → ≥5h → 通过
2. 规则5（中转接驳因果检查优先）：hardcheck检测到联程改签场景，因果检查确认前序航班确实延误导致误机，但因已改签且非旅客自身原因，不触发免责
3. AI审核：hardcheck返回通过 → AI审核判定通过

**人工逻辑**：
1. 人工看的是**原航班MS878自身延误**：3h22m < 5h → 不赔
2. 同时引用中转接驳免责条款
