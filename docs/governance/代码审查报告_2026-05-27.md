### ⚠️ 需关注

**P0-1：数据库连接无 TLS 加密（scripts 层）**

- 位置：`scripts/review.py:145-148`、`scripts/push.py:54-60`、`scripts/query.py:61-68`

所有脚本直接使用 `pymysql.connect()` 且未配置 SSL 参数，凭据和数据在网络上明文传输：

```python
conn = pymysql.connect(
    host=os.getenv("DB_HOST", ""),   # 空字符串默认走 localhost
    port=int(os.getenv("DB_PORT", "3306")),
    user=os.getenv("DB_USER", ""),
    password=os.getenv("DB_PASSWORD", ""),
    database=os.getenv("DB_NAME", "ai"),
    charset="utf8mb4",
    # 缺少: ssl={'ca': '/path/ca.pem', 'verify_identity': True}
)
```

**建议：** 添加 `ssl` 参数强制 TLS；在连接前校验 `DB_HOST` 和 `DB_PASSWORD` 非空；统一封装 `scripts/_common/db_utils.py`。

---

**P0-2：`ssl=False` 跳过 TLS 证书验证**

- 位置：`app/engine/material_extractor.py:220-224`

```python
async with session.get(url, proxy=proxy, ssl=False, timeout=aiohttp.ClientTimeout(total=60)) as resp:
```

从 Salesforce/外部 URL 下载理赔材料图片时完全禁用证书验证，存在中间人攻击风险。攻击者可注入恶意图片进入 OCR/Vision 流程。

**建议：** 移除 `ssl=False`，使用默认证书验证。如内部 S3 需要自签名证书，配置 `ssl.SSLContext(ssl.PROTOCOL_TLS_CLIENT)` 并加载自定义 CA。

---

**P0-3：`json_repair` 未限制输入大小**

- 位置：`app/openrouter_client.py:107`

```python
return json.loads(repair_json(content)), False
```

AI 返回的 JSON 解析失败时调用 `json_repair` 的 `repair_json`。该库对深度嵌套输入存在栈溢出风险（已有过安全通告），而系统未对输入长度做限制。

**建议：**
```python
if len(content) > 500_000:
    raise ValueError("响应过长，跳过 JSON repair")
return json.loads(repair_json(content, strict=False)), False
```

## 三、并发与竞态条件

**P1-1：Reviewer 实例共享导致竞态条件**

- 位置：`app/runner.py:61, 143`

```python
# runner.py:143 — 全局创建单个 reviewer
reviewer = AIClaimReviewer()

# runner.py:61 — 每个案件调用 set_claim_type 修改共享状态
reviewer.set_claim_type(claim_type)
```

`reviewer` 的 `self.module`、`self.prompt_namespace`、`self.ocr_service` 等属性被 `set_claim_type()` 修改。在 `asyncio.gather()` 并发 3 个案件时，如果案件类型不同（如一个 flight_delay、一个 baggage_delay），两者会竞争修改 `reviewer` 的状态，导致 prompt 命名空间或 OCR 缓存混乱。

**建议：** 在 `review_claim_async()` 内部创建独立的 `AIClaimReviewer` 实例，或使 `set_claim_type` 返回新实例而非修改自身。

---

**P1-2：`create_or_update_result` 存在 TOCTOU 竞态条件**

- 位置：`app/db/database.py:263-294`

```python
await cursor.execute(f"SELECT id FROM {TABLE_REVIEW_RESULT} WHERE forceid = %s", ...)
existing = await cursor.fetchone()
if existing:
    # UPDATE
else:
    # INSERT  ← 两个并发请求可能同时走到这里
```

autocommit=True 模式下，两个并发写入同一个 forceid 会同时看到"不存在"，都执行 INSERT 导致重复键冲突。

**建议：** 改用 `INSERT ... ON DUPLICATE KEY UPDATE`（`ClaimStatusDAO` 已使用该模式）。

## 四、逻辑错误与边界条件

**P1-3：`_run_hardcheck` 异常吞噬导致校验静默跳过**

- 位置：`app/modules/flight_delay/stages/hardcheck.py:986-988`

整个 900+ 行函数被单个 try/except 包裹：

```python
except Exception as e:
    result["debug_notes"].append(f"hardcheck异常: {e}")
    LOGGER.warning(f"[_run_hardcheck] 硬校验异常: {e}", ...)
return result
```

如果硬校验在第 500 行抛出异常，后面 400+ 行校验全部跳过，但下游 `postprocess.py` 会把未执行的空 dict 当成"无问题"。

**建议：** 将硬校验拆分为独立阶段，每个阶段有自己的 try/except，确保一个校验失败不影响其他校验。

---

**P1-4：`cmd_sync_db` 跳过历史记录追踪**

- 位置：`scripts/push.py:219-237`

批量同步只写 6 个字段（forceid, claim_id, remark, is_additional, key_conclusions, raw_result），完全绕过 `write_ai_history_if_changed()`，导致重跑案件时无法在 `ai_review_history` 表保留旧版本。

**建议：** 在批量插入后读取变更行，调用 `write_ai_history_if_changed()` 补齐历史记录。

---

**P1-5：SQL 构建缺乏白名单校验**

- 位置：`app/db/database.py:283`

```python
sql = f"""UPDATE {TABLE_REVIEW_RESULT} SET {', '.join(update_fields)} WHERE forceid = %s"""
```

虽然当前列名来自 `ReviewResult.to_dict()`（已知 dataclass），但缺乏显式白名单。若未来 `to_dict()` 返回动态 key，即成为注入点。

**建议：** 用 `_get_review_result_columns()` 返回的列名单校验 `result_dict.keys()`。

## 五、架构不一致问题

**P2-1：runner.py 硬编码只加载 baggage_damage 条款**

- 位置：`app/runner.py:146-148`

```python
policy_terms_file = POLICY_TERMS.resolve("baggage_damage")
with open(policy_terms_file, "r", encoding="utf-8") as f:
    policy_terms = f.read()
```

所有险种（flight_delay、baggage_delay）都收到了 baggage_damage 的条款内容。`scripts/review.py` 中已按险种加载正确条款，但 `main.py` 入口没有。

**建议：** 在批量循环内按 `claim_type` 加载对应条款。

---

**P2-2：`find_claim_folder` 每次都全目录扫描**

- 位置：`scripts/review.py:64-72`、`scripts/push.py:40-48`

```python
def find_claim_folder(forceid: str) -> Path | None:
    for info_file in CLAIMS_DIR.rglob("claim_info.json"):  # 每次全量扫描
```

在批量重跑时，每调用一次就全目录扫描一次，O(n×m) 次文件系统操作。

**建议：** 脚本启动时构建一次 `{forceid: folder_path}` 索引，后续 O(1) 查询。

---

**P2-3：日期解析逻辑分散在 5+ 个文件**

| 位置 | 函数 |
|------|------|
| `app/rules/common/policy_validity.py` | `_parse_date()`, `_parse_dt()` |
| `app/modules/flight_delay/stages/utils.py` | `_parse_date_str()`, `_parse_utc_dt()`, `_parse_local_dt()` |
| `app/modules/baggage_delay/stages/utils.py` | `_parse_dt_flexible()`, `_extract_date_yyyy_mm_dd()` |
| `app/db/models.py` | 多个 `from_dict()` 中的内联日期解析 |
| `app/db/database.py` | `_parse_datetime()` |

**建议：** 统一到 `app/utils/datetime_utils.py`。

---

**P2-4：Config 类属性在 import 时固化**

- 位置：`app/config.py:20-193`

所有配置是类属性，`load_dotenv()` 在模块导入时执行。测试中修改 `os.environ` 不会反映到 `Config` 类。且 `config` 全局实例（line 193）从未被使用——所有访问都是通过 `Config.DB_HOST` 类属性。

**建议：** 添加 `reload()` 方法或改用惰性属性。

---

**P2-5：`datetime.now()` 全局无时区信息**

- 位置：`app/db/models.py:100`、`app/db/database.py:105`、`app/db/history_helpers.py:106`

所有时间戳都是 naive datetime，跨时区运行或与 MySQL 比较时可能出现时差问题。

**建议：** 使用 `datetime.now(timezone.utc)` 统一存储 UTC，展示时再转换。
